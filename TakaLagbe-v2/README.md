# TakaLagbe! v2.0

A digital money transaction system: send money, pay bills, recharge, save,
split bills and settle up, with a full back office for the operator.

Built as the **CSE370 Database Systems** project at BRAC University.
PHP 8 and MySQL, no framework, no Composer, no CDN. The whole thing runs
from a plain XAMPP folder with the network unplugged.

---

## Running it

1. Copy this folder into `C:\xampp\htdocs\`.
2. Start **Apache** and **MySQL** from the XAMPP control panel.
3. Open phpMyAdmin, go to **Import**, choose `takalagbe.sql` and run it.
   The file creates the `takalagbe` database itself, so there is nothing to
   set up first.
4. Open <http://localhost/TakaLagbe-v2/>.

If your MySQL user is not `root` with an empty password, change the four
constants at the top of `config/config.php`.

**Admin console:** <http://localhost/TakaLagbe-v2/admin_login.php> ·
username `admin`, password `admin123`.

Sign up a normal customer through the app. You will be asked for a password
and a separate six digit transaction PIN; the PIN is what protects every
payment.

## What it does

### Money

| Feature | Notes |
|---|---|
| Send money | Free between users, up to ৳25,000 a transfer |
| Add money | From a linked bank or card, free |
| Cash in | At an agent point, free, the agent's float goes up |
| Cash out | At an agent point, 1.85% charge, the agent's float goes down |
| Mobile recharge | Operator detected from the prefix, 1% cashback |
| Bill payments | Electricity, gas, water, internet; flat ৳5 charge; the same bill cannot be paid twice for one month |
| Education fees | Semester payments to registered institutes; one student ID pays a semester once |
| Merchant payments | Each merchant carries its own cashback rate |

### Everyday

- **Savings goals** with a target, a deadline and a progress bar. Money in a
  goal leaves the spendable balance, so it cannot be spent by accident.
- **Request money** from one person, or **split a bill** any number of ways;
  every share becomes its own request and the whole batch is tracked together.
- **Favourites** for one tap sending, with suggestions based on who you
  actually send to.
- **QR codes**: show yours to be paid, scan someone else's to pay them. The
  code is generated by the application itself: see the note further down.
- **Notification centre**, unread badge, mark read, clear.
- **Insights**: category donut, six month in and out trend, who you send to
  most, busiest day, largest payment, cashback earned, declined attempts.
- **History** with search, type and direction filters, a date range and
  pagination.
- **Statements** you can print straight to PDF from the browser, or download
  as CSV with a UTF‑8 BOM so Excel reads Bangla correctly.
- **Receipts** for every transaction, with a QR code that encodes the
  reference and amount for verification.
- **Dark mode**, remembered per browser, and a layout that works down to a
  390 pixel phone.

### Admin

- Platform overview: users, money held, volume, charges collected, cashback
  paid, net revenue, a fourteen day volume chart and a product mix donut.
- User management: search, freeze, unfreeze, adjust a daily limit.
- Billers, merchants, cashback rates and agent floats.
- Institutes and every education fee collected.
- Support desk: read a ticket, reply into the customer's notifications, close
  or reopen it.
- Audit log, declined transactions with the reason, and repeated failed sign
  ins grouped by address.

## How the money is kept safe

**Every taka moves through one function.** `lib/money.php::move_money()` is the
only code that writes to the `account` table.

**The debit, the credit and the ledger row are one transaction**, so a crash
cannot take money from one side without it arriving at the other.

**Both accounts are locked before a balance is read:**

```sql
SELECT phone, balance FROM account WHERE phone = ? FOR UPDATE
```

They are locked in phone-number order, so two transfers going opposite ways
cannot end up waiting on each other. The daily limit and the velocity counter
are checked after the lock is taken, so they cannot be beaten by sending two
requests at once.

The test suite fires two ৳800 transfers from a ৳1,000 balance at the same
moment from two threads. One succeeds, the balance lands on ৳200.

**The rest:**

- Passwords and PINs are bcrypt hashes (`password_hash` / `password_verify`).
- Every query is prepared; PDO runs with `ATTR_EMULATE_PREPARES => false`.
- Every form carries a CSRF token, checked with `hash_equals`.
- Output goes through `e()`, so a `<script>` in a note prints as text.
- Five wrong sign-ins lock a number for fifteen minutes; five wrong PINs freeze
  the account and notify the owner.
- `session_regenerate_id(true)` on sign in, and an `HttpOnly` session cookie.
- Money columns are `DECIMAL(12,2)`, with `CHECK (balance >= 0)` underneath.
- Refused transactions are written to the ledger with `status = 'failed'` and
  the reason, and `audit_log` records who did what.

## The data model

Eighteen tables. The decisions worth explaining:

- **`bill_payments` replaces four near identical tables.** `electricity_bills`,
  `gas_bills`, `water_bills` and `internet_bills` were the same six columns
  four times over. They are one table now with a `billtype` column, and the
  four pages share one engine in `lib/bills.php`.

- **`user` and `account` are one to one**, with a foreign key and
  `ON DELETE CASCADE`, so a wallet cannot outlive its owner. Signup creates
  both inside one transaction, so a user can never exist without a wallet.

- **Eleven foreign keys**, mostly `ON DELETE CASCADE ON UPDATE CASCADE`, so
  deleting a user takes their wallet, favourites, goals, requests,
  notifications, bills, fees and recharges with them. The file brackets itself
  with `SET FOREIGN_KEY_CHECKS = 0 … 1`, so it imports cleanly over an existing
  database as well as into an empty one.

- **`transactions` deliberately has no foreign key.** `transaction_from` and
  `transaction_to` hold either a phone number or a name: "Titas Gas Limited",
  "Savings: New laptop": because a ledger row has to stay readable after the
  counterparty is edited or removed. It is denormalised on purpose; everything
  else uses a real key.

- **Two triggers keep the running totals.** `trg_bill_payment_total` and
  `trg_education_fee_total` add each new payment to the biller's
  `total_received_amount`, so that column cannot drift away from the rows it
  summarises. It used to be an `UPDATE` in PHP after every insert.

- **`login_attempts` has a `kind` column** (`login`, `admin` or `pin`) rather
  than one column holding `admin:someone` and another holding `pin:127.0.0.1`.
  One column, one meaning.

- Supporting tables: `favourites`, `savings_goals`, `money_requests` (with a
  `split_group` tying a split bill batch together), `notifications`,
  `login_attempts`, `audit_log`, `admin`, `merchants`, `organizations`,
  `institutes`, `education_fee`, `mobile_recharge`, `agent_details`,
  `support_messages`.

Lines marked **FK** are enforced by a foreign key. The two that are not are the
ledger joins described above.

```
                          +-----------+
                          |   user    |
                          +-----------+
                            |       |
                  1 FK      |       |      * FK
              +-------------+       +--------------------+
              |                                          |
        +-----------+                +----------------------------------+
        |  account  |                | favourites     savings_goals     |
        +-----------+                | notifications  money_requests    |
              |                      | support_messages  agent_details  |
              | * (by phone,         +----------------------------------+
              |    not a key)                            |
              |                                          | * FK
        +--------------+             +----------------------------------+
        | transactions |             | bill_payments    education_fee   |
        +--------------+             | mobile_recharge                  |
              ^                      +----------------------------------+
              |                            * |  FK        * |  FK
              | by name              +---------------+  +------------+
        +-----------+                | organizations |  | institutes |
        | merchants |----------------+---------------+  +------------+
        +-----------+

   money_requests.split_group ties one split bill batch together
   login_attempts, audit_log, admin are standalone
```

## About the QR code

`lib/qr.php` builds the QR code itself rather than calling a library: byte
mode, error correction level L, versions 1 to 10, Reed-Solomon over GF(256),
all eight mask patterns scored against the four penalty rules in
ISO/IEC 18004, written out as an SVG.

This is more than the project needed: a library would have done. I wrote it
because I wanted to know how a QR code actually works, and it is the part of
this project I learned the most from. If you are reading the code, that file
is the one to ask me about.

## Layout

```
takalagbe/
├── config/
│   ├── config.php        every tunable number: limits, fees, cashback
│   ├── db.php            the PDO connection and four query helpers
│   └── helpers.php       session, auth guard, CSRF, flash, formatting, audit
├── lib/
│   ├── money.php         the money engine, the only thing that writes balances
│   ├── bills.php         one engine behind all four bill pages
│   ├── qr.php            the QR encoder
│   └── view.php          shared rendering for a transaction row and the charts
├── Assets/
│   ├── css/app.css       the whole design system, light and dark
│   └── js/app.js         plain JavaScript, no library
├── Front_end/
│   ├── partials/         head, nav, foot, admin nav
│   └── front_*.php       one view per page
├── tests/e2e.py          82 end to end checks against a running server
├── *.php                 one controller per page
└── takalagbe.sql         the schema and the reference data
```

Every page follows the same shape the original project used: a controller at
the root does the work, then includes its view from `Front_end/`.

## Tests

`tests/e2e.py` drives the real application over HTTP the way a browser would,
then checks the database behind it.

```bash
php -S 127.0.0.1:8080 -t .          # in one terminal
python3 tests/e2e.py                # in another
```

The suite finds the MySQL client itself, so it works with XAMPP as well as with
a system MariaDB. If it is not on your PATH, point it at the binary:

```
set TKL_MYSQL=C:\xampp\mysql\bin\mysql.exe
```

82 checks covering signup and sign in, every money flow and its arithmetic,
the charges and the cashback, the caps and the daily limit, savings, requests,
split bills, the admin console, and:

- CSRF forgery is rejected
- SQL injection in a form field and in the search box does nothing
- a script tag in a note is escaped
- five wrong PINs freeze the account
- repeated bad sign ins lock the number
- one user cannot open another user's receipt
- two simultaneous transfers cannot overdraw an account
- no balance is ever negative and every transaction id is unique
- a trigger keeps a biller's total in step with its payment rows
- awkward inputs: a very long name, note, goal title or admin username
